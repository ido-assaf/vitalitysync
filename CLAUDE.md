# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What is the active app

**VitalitySync** is a full-stack fitness & nutrition app. Only two directories are the live application:

- `backend/` — Node.js + Express + Sequelize (MySQL) + Socket.IO + Groq AI
- `frontend/` — React 18 (Create React App)

Everything else in the repo root is **not** part of the running app and should be left alone unless asked: `app/` + `.venv/` + `__pycache__/` (an older Python assignment), `fitness_app.db` (stale SQLite), and the `assignment*.zip` / `*.mp4` submission artifacts. The active persistence layer is MySQL, not the SQLite file.

## Commands

All commands run from `backend/` or `frontend/` (never the repo root).

### Backend
```powershell
cd backend
npm install
Copy-Item .env.example .env      # then fill in DB_* and GROQ_API_KEY
npm start                        # runs node src/server.js -> http://localhost:3000
npm test                         # Node built-in test runner over an explicit file list
```
- **Single test file:** `node --test tests/aiService.test.js` (the `test` script passes `--test-isolation=none` and an explicit list of files — new test files must be added to that list in `package.json` to run under `npm test`).
- Schema/data scripts are one-off and destructive-adjacent; back up first: `npm run migrate:ai-coaches`, `npm run migrate:nutrition`, `npm run repair:schema`, `npm run finalize:demo`, `npm run normalize:demo-metric`.

### Frontend
```powershell
cd frontend
npm install
Copy-Item .env.example .env      # set REACT_APP_API_BASE_URL / REACT_APP_SOCKET_URL
npm start                        # set PORT=3001 in .env if backend owns 3000
npm test                         # react-scripts (jest), non-watch
npm run build
```
- **Single test:** `npx react-scripts test Onboarding` (filters by filename).

### First-time DB bootstrap
Create an empty MySQL DB (`utf8mb4`), then for the first local run set `DB_SYNC=true DB_SEED=true` in `backend/.env`; switch both to `false` afterward. See README.md for the full env-var table and MySQL setup.

## Architecture

### Backend entrypoint indirection
`backend/server.js` **is** the real Express app — it builds `app`, mounts every router, and exports both `app` and `startServer()`. `backend/src/server.js` is a thin wrapper that re-exports it and is what `npm start` runs. When editing server bootstrap, routing, CORS, or middleware, edit `backend/server.js`.

### Uniform response envelope (load-bearing)
Every response goes through `backend/models/response.js`: success is `{ success, data, error: null }`, failure is `{ success: false, data: null, error: { code, message, details } }`. The frontend's `frontend/src/services/api.js` `unwrapResponse` throws on `success: false` and returns `.data`, so **breaking the envelope silently breaks the whole frontend**. Error `code` strings (e.g. `VALIDATION_ERROR`, `NOT_FOUND`, `FORBIDDEN`) propagate to `error.code` on the client. CORS preflight (`OPTIONS`) intentionally returns an empty `204`.

### Auth is header-based, not JWT
There are no sessions or tokens. The frontend stores the logged-in user in `localStorage["vitalitysyncUser"]` and `api.js` attaches `x-user-id` and `x-user-role` on every request. The backend `middleware/auth.js` `authorizeRoles(...)` guards routes purely on the `x-user-role` header. Admin identity is `User.userRole === "admin"` — the `Admin` model is a minimal one-to-one profile and is **not** the source of authorization. Socket.IO role/userId likewise come from the handshake query (untrusted). Treat this as intentional for the course project; don't "harden" it unless asked.

### CRUD factory pattern
Simple resource controllers are generated by `backend/utils/resourceControllerFactory.js` (`createCrudController`) which produces `list/getById/create/update/remove`, each wrapped in `utils/asyncHandler.js` and using helpers from `utils/controllerHelpers.js`. Prefer extending this factory (via `validateBody` / `buildCreatePayload` / `buildUpdatePayload`) over hand-writing standard CRUD. Controllers with real logic (nutrition, workoutPlans, adminDashboard, ai) are written by hand.

### Models & associations
All Sequelize models live in `backend/models/`; **every association is declared centrally in `backend/models/index.js`** — add relationships there, not in individual model files. `sequelize` uses `freezeTableName: true`. `WorkoutPlanExercise` is the join table for the WorkoutPlan↔Exercise many-to-many and also stores per-day ordering (`dayLabel`, `orderIndex`, `targetSets`, `targetReps`). Users self-reference via `coachId` (Coach/Trainees).

### DB initialization sequence
`config/initializeDatabase.js` runs on startup: `authenticate()` → conditional `sync({ alter })` (gated by `DB_SYNC`/`NODE_ENV`) → optional seed (`DB_SEED`) → then **always** runs the idempotent `migrateAiCoachArchitecture` and `migrateNutritionArchitecture` scripts. Those two migrations run on every boot, so they must stay safe to re-run.

### Real-time workout monitoring (Socket.IO)
`backend/services/socketService.js` owns all live workout logic. Rooms: admins join `admin-monitoring`; each trainee joins `trainee-workout:<userId>`. Events (`workout:started`, `setLog:created`, `workout:progressUpdated`, `workout:issueReported`, `workout:coachResponse`, `workout:finished`) are validated, **persisted through Sequelize**, then re-emitted to the admin room and/or the trainee room. `workout:coachResponse` is admin-only. Frontend client is `frontend/src/services/socket.js` (`createWorkoutSocket(role)`); admin UI is `pages/AdminDashboard.jsx`, trainee UI is `pages/Training.jsx`.

### AI layer (backend-only)
The Groq API key never leaves the backend. `backend/services/aiService.js` calls Groq chat + vision models (all requests go through its `callGroqJson` client) and parses free-form model output with a brace-matching `extractJson` + strict `normalize*` validators before anything is returned or persisted — always validate AI output this way rather than trusting it. Nutrition food data comes from `openFoodFactsService.js`. Temporary AI evaluation/estimate snapshots live in in-memory stores (`nutritionEvaluationStore.js`, `nutritionEstimateStore.js`) and **vanish on restart**; only explicitly-saved records reach MySQL. Note there are two nutrition stacks: the live one (Open Food Facts + `NutritionLogItem` via `/nutrition/*`) and a legacy assignment-era one (`FoodProduct`/`ProductEvaluation`/`MealPlan` CRUD) kept only for the course API contract.

### AI Specialist capability pipeline
This is the newest and most involved subsystem. `backend/utils/aiSpecialistCapabilityRegistry.js` is the **single source of truth** for which coach domains are `available` vs `coming_soon`, whether each is workout-assignable / nutrition-available, and its `plannerType` / `ruleSetId` / `knowledgeTags`. Currently only `strength training` (fitness) and `sports nutrition` are `available`; the rest are gated `coming_soon`.

The planning pipeline (invoked from `controllers/workoutPlansController.js` `suggest` and `controllers/nutritionController.js`) chains, in order:
1. `coachIntakeService.js` — normalize/summarize trainee intake text & lists.
2. `aiSpecialistContextService.js` — assemble fitness or nutrition context from trainee profile, workout/session/issue history, and nutrition logs.
3. `aiSpecialistRuleService.js` — derive `hardStops` / `warnings` / `recommendedAdjustments` / `explanationHints` per the capability's rule set.
4. `aiSpecialistKnowledgeService.js` (backed by `aiSpecialistKnowledgeBase.js`) — retrieve relevant knowledge items by tag.
5. `aiSpecialistPlanningModifierService.js` — apply **bounded** score adjustments (deltas capped by `MAX_SOFT_SCORE_DELTA` / `MAX_TOTAL_SCORE_DELTA`) so AI guidance can nudge but not dominate the plan.

When adding a new coach type or capability, update the registry first; the context/rule/knowledge/modifier services and their tests key off its fields.

## Conventions
- Backend tests use the **Node built-in test runner** (`node:test` + `node:assert`), not Jest — and are currently unit tests of services/utils (no live DB). Add any new backend test file to the `test` script list in `backend/package.json`.
- Frontend tests are colocated (`*.test.jsx` / `*.test.js`) and use React Testing Library via `react-scripts`.
- Route → controller → service → model is the standard layering; keep DB access in models/services, HTTP shaping in controllers.
- Only `.env.example` files are committed; never commit real `.env`, DB credentials, or the Groq key.
